# Полный разбор нашего GraphRAG

После отдельного запроса код отформатирован, комментарии отредактированы; логика и строковые значения сохранены. Описанные недостатки не исправлялись. Номера строк ниже — из первичного аудита; актуальные позиции см. в [карте строк](checks/code_cleanup/line_map.json).

## 1. Главная мысль для ревью

**Мы сделали локальный учебный QA-прототип по научным абстрактам: arXiv → LLM-экстракция → Neo4j → поиск статей → абстракты и связи → ответ LLM → FastAPI.**

Самая точная характеристика текущей реализации: **RAG по абстрактам с графовым обогащением контекста**. Это не полная реализация Microsoft GraphRAG, не community-based global search и не доказанная multi-hop система.

Что удалось: собрать end-to-end pipeline, сохранить происхождение связей, исправить направление рёбер, сделать точечную безопасную миграцию алиаса, устранить конкретный retrieval-промах, добавить тестируемую абляцию графового контекста.

Что пока не удалось доказать: что добавленные связи повышают качество ответов. На пяти development-вопросах явного выигрыша нет. Этот честный результат полезнее выдуманного процента улучшения.

### Границы

- Источник — **title и abstract**, не полные PDF.
- Предметная область — небольшой срез arXiv `cs.CL`, а не вся научная литература.
- Пользовательские вопросы и ответы — английские. Старый русский `eval.py` — исторический эксперимент, не текущая спецификация.
- Внешние сервисы локальные: Neo4j и Ollama. Воспроизводимость всё равно зависит от моделей, версий, hardware и состояния данных.
- UI нет и не требуется. Интерфейс — HTTP API и скрипты.
- Аудит не меняет бизнес-логику. Все рекомендации ниже нужно внедрять отдельно.

## 2. Архитектура: две разные стадии

### 2.1. Подготовка данных — offline

```text
arXiv Atom API
  └─ fetch_papers.py → data/papers.json
       └─ extraction.py → extract_triplets.py → Ollama/Qwen
            └─ data/triplets.jsonl
                 └─ load_graph.py → Paper, Entity, MENTIONS, R
                      ├─ add_abstracts.py → Paper.abstract
                      └─ embeddings.py → Entity.embedding, Paper.embedding

entity_names.py → согласованный alias mapping при загрузке
qa.create_paper_index → paper_vec (отдельный шаг текущего bootstrap)
Laya-скрипты → экспериментальная боковая ветка, не обязательный gate
```

**Зачем разделять стадии:** дорогая экстракция и embedding корпуса выполняются не на каждый вопрос. На запросе считаем только embedding вопроса, ищем данные и генерируем ответ.

### 2.2. Ответ на вопрос — online

```text
POST /ask {"question": "..."}
  → app.py: Pydantic + общие driver/model
  → qa.prepare_context:
      encode(question)
      → retrieval.retrieve_papers: ANN + точные идентификаторы в title
      → 3 статьи
      → qa.graph_context: до 30 извлечённых отношений этих статей
  → qa.build_prompt: правила + факты + полные абстракты + вопрос
  → qa.generate_answer → Ollama/Qwen
  → {"question": "...", "answer": "..."}
```

Чего **нет** в online-пути: поиска по embeddings сущностей, обхода нескольких hops, поиска новых статей по соседям, reranker-модели, BM25, RRF, генерации community summaries. Наличие `entity_vec` и функции `vector_search_entities` не означает, что они используются в `ask`.

### 2.3. Как выглядит граф

```text
(:Paper {id, title, abstract, embedding})
   -[:MENTIONS]->
(:Entity {name, embedding, aliases?})
   -[:R {type: "USES", source_ids: [paper_id, ...]}]->
(:Entity)
```

- `Paper.id` и `Entity.name` защищены uniqueness constraints.
- Физический тип отношения — `R`; смысловой предикат хранится в свойстве `type`.
- `MENTIONS` означает «статья упоминает сущность», а не «доказывает все связи этой сущности».
- `source_ids` у `R` связывает утверждение с конкретными статьями. Это provenance, не probability и не ручное подтверждение.
- Направление важно: `A USES B` не равно `B USES A`; `A EXTENDS B` не равно `A IMPROVES B`.
- Одна связь может иметь несколько источников, поэтому число фактов не равно числу подтверждений.

**Пример, условный, не запись из корпуса:** статья P говорит «Method A uses encoder B». Узлы A и B связаны `A -R{type: USES, source_ids:[P]}-> B`; P указывает на оба узла через `MENTIONS`.

### Как объяснить расхождения

- **500 ≠ 498:** две статьи отсутствуют среди результатов extraction. По текущим файлам нельзя достоверно восстановить причину каждого пропуска; не говорить «точно timeout», если нет соответствующего лога.
- **522 ≠ 498:** JSONL содержит повторные записи 24 IDs. Resume смотрит только состояние на старте и не гарантирует отсутствие дублей.
- **3113 ≠ 3004:** есть повторяющиеся записи связей. Кроме того, граф делает `MERGE` по направленной тройке, а provenance хранит отдельно. Совпадение числа уникальных per-paper троек с числом `R` в этом снимке — наблюдение, не общая формула.
- **13 изолированных статей:** загрузчик создаёт Paper и при пустом наборе связей. Изолированная статья всё ещё может участвовать в paper retrieval, если имеет embedding.
- **16 самосвязей:** повод для ручного разбора, не автоматического удаления. Например, после канонизации два имени могут оказаться одним узлом; но нельзя приписать все 16 этой причине без проверки.
- **Варианты имён:** `Large_language_models`, `Large language models` и прочие формы фрагментируют граф. Простое lowercasing не решает омонимы, аббревиатуры и различия смысла.

### Коварное ограничение embeddings

`all-MiniLM-L6-v2` создаёт **384-мерные** векторы, но `max_seq_length` в текущем окружении — **256 токенов**. Это разные характеристики: размер вектора не равен числу входных токенов.

Из 500 текстов `title + ". " + abstract` **388** превышают лимит; самый длинный — **547** токенов. Embedding-модель обрезает вход, поэтому поздние детали abstract могут не участвовать в поисковом представлении. При генерации полный abstract всё равно передаётся в prompt; это не доказательство обрезания генератором.

Что делать позже: измерить качество на длинных статьях; сравнить chunking, abstract summarization или другую embedding-модель. При смене модели нужно пересчитать корпусные векторы и пересоздать/проверить индекс; нельзя просто кодировать вопросы другой моделью.

## 4. Что сделано хорошо

### 4.1. Есть законченный вертикальный срез

Проект не ограничивается ноутбуком: данные доходят от arXiv до HTTP-ответа. Можно отдельно показать ingestion, retrieval, граф и generation. Это хорошая учебная база для обсуждения границ компонентов.

### 4.2. Сохраняются абстракты и provenance

`qa.py:30–49` требует одновременно выбранную статью и её ID в `r.source_ids`. Это защищает от ситуации «у сущности есть какая-то связь из другой статьи — значит, найденная статья её подтверждает». Prompt прямо предупреждает о ненадёжности автоматических отношений.

Но источник на ребре — лишь указатель на доказательство, не само доказательство. Нужны evidence spans, версии экстрактора и проверки смысла.

### 4.3. Исправлена направленность

Граф не просто красивое хранилище: направление является частью значения. Исправление перевёрнутых рёбер — содержательный шаг. Текущий `_add_relation` сохраняет head → tail, а графовый контекст читает это направление.

### 4.4. Канонизация сделана консервативно

`entity_names.py` содержит только проверенный `ACTGCG → ActGCG`. Миграция не сливает все похожие имена автоматически: dry-run, backup, проверка snapshot, направления, объединение источников, отказ при конфликте метаданных, сохранение канонического embedding.

Это сильный пример инженерного мышления: «не умеем надёжно разрешать все сущности» лучше опасной универсальной эвристики.

### 4.5. Исправление retrieval локализовано

Embedding-промах на RAG-FGO компенсирован точным идентификатором в title, без необоснованной замены всей модели. Regex строится из экранированных токенов, данные передаются в Cypher параметрами; есть unit-тесты.

Ограничение: эвристика развивалась на знакомых вопросах. Для оценки обобщения нужны новые, заранее отложенные кейсы.

### 4.6. Оценка стала честнее

В `eval_graph.py` общие статьи заморожены до генерации; различие prompt-пары — только graph facts. Не передаются reference notes, чередуется порядок режимов, сохраняются prompts, usage, timings, errors и truncation. Поля семантического review изначально пустые.

Это хорошие инварианты эксперимента. Они не превращают пять development-кейсов в научный benchmark.

### 4.7. Тесты проверяют важные свойства

36 тестов покрывают чистую логику retrieval, планирование миграции и честность mini-eval. Особенно полезны отказ при конфликте, отсутствие reference leakage и различение ошибки генерации и корректного отказа отвечать.

## 5. Проблемы и улучшения по приоритету

Уровни: **P0 — до публикации/внешнего доступа**, **P1 — до уверенных заявлений о корректности и воспроизводимости**, **P2 — качество, масштаб и удобство**. Это относительная приоритизация учебного проекта, не CVSS-аудит.

### P0-1. Учётные данные и доступ к API

**Где:** `scripts/app.py:8–10`, `qa.py:8–12`, `load_graph.py:5–6` и другие Neo4j entrypoints; `.gitignore:1–10`.

**Факт:** credentials в коде, общего конфигурационного слоя нет. В API нет аутентификации, ограничений частоты или размера вопроса.

**Риск:** утечка доступа при публикации, дорогостоящие/длинные запросы при внешней экспозиции. Это не означает, что локальный API сейчас доступен из интернета: сетевую экспозицию этот аудит не подтверждал.

**План:** сменить текущие credentials; вынести URI/auth/models/timeouts в настройки окружения, добавить `.env.example` без значений секретов, игнорирование `.env` и выборочный staging. При внешнем доступе — auth, quotas, request limits и только необходимые сетевые права.

**Критерий готовности:** в tracked-файлах нет секретов; запуск с неполной конфигурацией даёт понятную ошибку; unauthorized-запрос не запускает модель.

### P0-2. Опасный инструмент пересборки

**Где:** `scripts/rebuild_relations.py:6–29,31–57`.

**Факт:** удаляет весь слой `R`, затем восстанавливает из текущего JSONL, а не из backup. Backup лишь читается по фиксированному пути и проверяется на непустоту.

**Хорошо:** удаление и восстановление внутри одной write-транзакции; несовпадение processed count вызывает rollback.

**Недостаточно:** непустой JSON не доказывает пригодность восстановления; не проверены схема, принадлежность нужной БД, дата и полнота backup. Входные nodes могут не соответствовать данным.

**План:** explicit `--apply`, dry-run, параметры путей, схемы/хеши, инварианты before/after, проверенный restore на копии БД. Не запускать в демо.

### P1-1. JSON-валидация не равна схеме и истине

**Где:** `scripts/extract_triplets.py:23–56`; свидетельства — `extra_evidence.json`.

Функция пропускает числовые entities, принимает `A IMPROVES A`, превращает неизвестный предикат в `RELATED_TO`; `entities: null` вызывает `TypeError`, элемент `relations: 42` — `AttributeError`. Эти исключения не входят в текущий retry-блок.

Даже идеальная схема не докажет `A IMPROVES B`: предложение «A uses B» не содержит такого вывода. Модель может выбрать правильные имена и неправильный смысл.

**План:** строгая модель типов, enum предикатов, nonempty strings, endpoint validation, причины отклонения; неизвестные отношения в quarantine вместо молчаливой подмены. Отдельный semantic review по evidence span, не только проверка JSON. Typed exceptions вместо `SystemExit` библиотечной функции, retries только для подходящих ошибок с backoff.

**Критерий:** malformed output не падает непредсказуемо и не попадает в граф; тесты есть и на форму, и на примеры неверного значения.

### P1-2. Ненадёжный resume extraction

**Где:** `scripts/extraction.py:8–33`.

`done` загружается один раз, после успешной записи не обновляется. Повторный ID в исходном списке может быть обработан повторно. Оборванная JSONL-строка на старте вызывает ошибку; несколько writers могут конфликтовать; нет версии prompt/model и статуса ошибок.

**План:** `done.add` после успешной фиксации; проверяемые записи с версиями, error journal; безопасное восстановление последней строки с сохранением повреждённого фрагмента; один writer/lock либо таблица заданий с уникальным ключом. Нельзя молча выбрасывать произвольные повреждённые строки.

### P1-3. Загрузка не атомарна на статью

**Где:** `scripts/load_graph.py:53–71`; `add_abstracts.py:5–14`.

`execute_write` вызывается отдельно для Paper, каждой Entity, MENTIONS и R. Сбой оставляет частичную статью; много round trips. `MERGE` уменьшает дубли, но не исправляет смысл и не удаляет старые факты при изменении extraction.

**План:** одна транзакция на статью или контролируемый batch через `UNWIND`; отчёты created/matched/rejected; версии ingestion и явная стратегия replacement. Сохранять многоисточниковую provenance при удалении устаревших утверждений.

### P1-4. Запуск нельзя воспроизвести одной командой

**Где:** пустой корневой `README.md`, `pyproject.toml:9–23`, `src/graphrag_papers/__init__.py:1–5`, `embeddings.py:56–63`, `qa.py:139–148`.

CLI entrypoint пока выводит строку; рабочие модули живут в `scripts/` и зависят от способа запуска/CWD. `embeddings.py` создаёт `entity_vec`, но не `paper_vec`; последний создаётся в demo-блоке `qa.py`. Bootstrap распределён между файлами.

Laya не объявлена среди core dependencies. Это допустимо для optional-эксперимента, но его воспроизводимость отдельно не оформлена. `uv.lock` фиксирует Python-пакеты, но не всю среду: Neo4j/Ollama, model revisions, corpus, hardware.

**План:** README, env example, схема bootstrap, проверка readiness индексов, модельных размеров и `ONLINE`; затем пакет `src/graphrag_papers/`, реальные команды, optional dependency group для Laya, версии сервисов и моделей.

### P1-5. API принимает бессодержательные вопросы и теряет ресурсы при startup error

**Где:** `scripts/app.py:12–36`; `api_contract.json`.

С моками получено: отсутствующий question → 422; пустой и пробельный → 200; лишнее поле → 200. Это не живая проверка качества ответа: `ask` подменён. Driver закрывается при нормальном shutdown, но не при исключении загрузки SentenceTransformer до `yield`.

**План:** trim + min/max length, согласованная политика extra fields; `try/finally` вокруг lifecycle ресурсов; понятные 502/503/504 для зависимостей; correlation IDs. `/health` сейчас возвращает константу, это liveness, не полная readiness.

Синхронный endpoint `def` исполняется FastAPI в threadpool; это не гарантирует достаточную concurrency. Нужны нагрузочные тесты и ограничение числа генераций. Простая замена на `async def` не сделает `requests.post` неблокирующим.

### P1-6. Доказательная база качества слишком мала

**Где:** `scripts/eval_graph.py:34–85,151–203`; сохранённый mini-eval.

Четыре answerable-вопроса и один out-of-scope, часть уже использовалась при отладке. Почти все решаются одним abstract, а не связями нескольких статей. Оценивал тот же ассистент, который помогал разрабатывать.

**План:** отложенный набор по категориям (названия, перефразировки, отношения, числа, cross-paper, неизвестное); человеческая разметка и слепое сравнение; отдельные retrieval/answer/citation metrics; paired repetitions и отчёт неопределённости. Reference evidence не включать в prompt генератора.

### P2-1. Поиск имён эвристический и плохо масштабируется

**Где:** `scripts/retrieval.py:14–91`.

Идентификаторы узнаются по ≥2 uppercase, дефису или `_`. Например, TextSphere попадёт благодаря T и S, а Bioformer без дефиса — нет: у него одна uppercase. Обычные слова в ALL CAPS могут попасть ошибочно; synonym/alias resolution нет.

Заголовки сканируются regex, подходящим для 500 статей. Точное совпадение по title приоритетнее cosine: это правило, не обученный reranker, не BM25/RRF.

**План:** full-text индекс, словарь approved aliases, нормализация; более широкий candidate pool, lexical+dense fusion и reranking — только после оценки. Нельзя обещать ускорение или качество без измерения.

### P2-2. Граф не используется для расширения evidence

**Где:** `scripts/qa.py:30–49,63–70`.

Сначала выбираются 3 статьи, потом берутся только их отношения. Набор документов графом не расширяется. `ORDER BY head, rel, tail LIMIT 30` детерминирован, но алфавитная обрезка не учитывает релевантность вопросу. Извлечённые связи могут повторять abstract или добавлять шум.

**План:** question-aware selection фактов, явный бюджет, evidence spans; затем отдельный эксперимент с ограниченным multi-hop expansion и получением дополнительных источников. Контроль branch factor, циклов, provenance и стоимости обязателен.

### P2-3. Качество сущностей и онтологии

**Где:** `scripts/entity_names.py:1–6`, `extract_triplets.py:7–21`; `graph.json`.

Сейчас нет entity types, document-level evidence span, формальной семантики каждого предиката. `RELATED_TO` размывает интерпретацию. Автоматическое слияние похожих строк опасно.

**План:** glossary predicates с примерами/контрпримерами; candidate aliases → ручная проверка → versioned mapping; отчёт самосвязей и orphan nodes; для claims хранить provenance на уровне отдельного assertion, если появятся conflicting evidence или числа.

### P2-4. Бюджеты и наблюдаемость

**Где:** `scripts/qa.py:14–19,102–137`; `embeddings.py:21–54`.

Generation diagnostics сохраняются в eval, но обычный API возвращает только строку. Prompt budget не считается заранее; truncation flag покрывает `done_reason=length` выхода, а не гарантирует сохранение всего входа. Все embeddings и records обрабатываются крупными списками — допустимо на сотнях, не на миллионах.

**План:** этапные timings, tokens, queue metrics, ошибки и источник ответа в структурированном internal result; API contract решить отдельно. Batch/streaming ingestion, лимиты и backpressure; измерения p50/p95. Не логировать секреты и произвольные пользовательские данные без политики.

## 6. Laya: эксперимент, а не гарант истины

Текущая роль Laya — проверка, поддерживается ли тройка абстрактом. Она не входит в `qa.ask`, а `load_graph.py` читает исходный `triplets.jsonl`, не `triplets_filtered.jsonl`.

Два разных протокола нельзя смешивать:

1. `laya_filter.py`: `type="noul"`, числовой результат и threshold 0.5, общий вопрос о поддержке отношения.
2. `eval_laya.py`: `type="choice"`, A/B, более конкретные инструкции про направление и различие использования/улучшения.

Показатель второго протокола не доказывает качество первого.

### Сохранённый результат

Из 20 AI-assisted размеченных случаев: 3 A, 15 B, 2 U. U исключены из оценки, остаётся 18.

| Метрика | Значение | Интерпретация |
|---|---:|---|
| TP | 3 | Поддерживаемая связь принята |
| FP | 8 | Неподдерживаемая связь принята |
| FN | 0 | Поддерживаемая связь отвергнута |
| TN | 7 | Неподдерживаемая связь отвергнута |
| Precision | 3 / 11 = 27.3% | Большинство принятых связей здесь неверны по разметке |
| Recall | 3 / 3 = 100% | Всего три положительных случая, слабое основание для обобщения |
| Accuracy | 10 / 18 = 55.6% | Ниже always-B на этой выборке: 15 / 18 = 83.3% |

Always-B имеет нулевую полноту по A, поэтому одна accuracy тоже не достаточна. И нельзя делать вывод о всей библиотеке по маленькому смещённому набору.

### Почему оценка предварительная

- Разметка сделана с помощью ИИ, не согласована независимыми annotators. «Не подтверждено abstract» не обязательно «ложно в мире».
- Часть строгих онтологических ожиданий не была явно передана в инструкции. Нужно различить ошибку модели и несовпадение задачи.
- В сохранённых строках нет `usage.truncated`, token budget и полной версии окружения. Предыдущая offline-реконструкция обнаружила риск обрезания claim в одном примере; это не записанная телеметрия исходного запуска и не доказанная причина всех ошибок.
- Пользовательская документация описывала Laya 0.4.21; проверенный SDK в кэше — 0.5.4. Нельзя автоматически переносить все обещания между версиями. Это отдельное окружение, не объявленная core dependency проекта.
- Для binary choice высокая вероятность варианта не доказывает истинность. `confidence = 1 − H(p)/log(K)` характеризует концентрацию распределения; `answer_confidence` может калиброваться, но калибровку нужно проверить на своей задаче.
- Предупреждение о множестве вариантов `choice:11+` само по себе не объясняет ошибки нашего `choice:2`.

**Решение:** не включать Laya как обязательный фильтр графа. Сначала фиксировать версии, полный state/questions/usage, обеспечивать видимость claim, уточнить правила, расширить и независимо проверить разметку, сравнить thresholds/abstention и baselines.

## 7. Что показывает последний mini-eval GraphRAG

### Что сравнивали

`retrieval_only` — те же title-aware/vector top-3 и абстракты, **без graph facts**. `graph_enriched` — они же **с graph facts**.

Это не «чистая LLM против RAG» и не «векторный поиск против графового поиска». Мы изолируем добавление текстовых отношений в уже найденный контекст.

### Результаты одного локального прогона

| Показатель | Без графовых фактов | С графовыми фактами |
|---|---:|---:|
| Успешных генераций | 5/5 | 5/5 |
| Ошибок / обрезанных ответов | 0 / 0 | 0 / 0 |
| Средняя wall-time генерации | 28.6 с | 47.4 с |
| Содержательных ответов со ссылкой на найденный источник | 1/4 | 1/4 |
| Явных побед по основному качеству в AI-assisted review | 0 | 0 |

Ожидаемая статья есть в top-3 для **4/4** answerable-кейсов. Это hit@3 по маленькой выборке, не 100%-ная точность системы и не recall по всем релевантным статьям.

### Пять кейсов

- **RAG-FGO:** оба режима описывают оптимизацию query rewriting и memory pool; существенной прибавки от графа не найдено, URL отсутствует.
- **Bioformer-RetroMAE:** MAP +37.0%, Recall@100 +29.1% воспроизведены верно; оба режима ошибаются в числе параметров. «40% от параметров» превращено в «на 40% меньше». Правильная арифметика: примерно **на 60% меньше**. URL есть.
- **TextSphere:** оба режима правильно описывают CLIP embeddings и AdaLN; URL нет.
- **ActGCG:** оба отвечают о suffix, оптимизированном под target activations. «Без white-box при генерации» не означает «без white-box при оптимизации». URL нет.
- **Цена GPU:** оба корректно отказываются выдумывать цену из нерелевантных abstracts.

### Правильный вывод

«На этих пяти development-вопросах добавление графовых фактов не продемонстрировало выигрыша в основном качестве и сопровождалось более долгой генерацией. Нужен больший отложенный набор, особенно для cross-paper задач».

**Неправильные выводы:** «GraphRAG бесполезен», «граф улучшает на X%», «у нас точность 100%», «temperature 0 гарантирует одинаковый ответ», «ссылка доказывает поддержку каждого утверждения».

Указанные времена — generation wall time одного запуска, не полная end-to-end latency, не p95 и не валидированный benchmark. Cache/load effects не устранены полностью.

## 8. Как улучшать без бесконечного переписывания

### Этап 1. Безопасность и воспроизводимость

Настройки и ротация credentials → README/bootstrap → безопасные миграции → optional Laya environment.

**Проверка:** новый разработчик на чистом окружении поднимает pipeline по инструкции; секретов в репозитории нет; destructive tools по умолчанию ничего не меняют.

### Этап 2. Корректность данных

Строгие схемы → recovery/resume → транзакция на статью → evidence/ontology → тесты с malformed/contradictory data.

**Проверка:** повторный ingestion не создаёт дубли, сбой статьи откатывает её запись, provenance не теряется, неверный relation не маскируется молча.

### Этап 3. Измерение качества

Новый набор с категориями → human review → dense/title ablation → graph-facts ablation → optional Laya eval. Сначала фиксировать baseline, потом выбирать улучшение.

**Проверка:** видны ошибки retrieval отдельно от generation, ссылки оцениваются по поддержке claims, есть out-of-scope и числовые кейсы.

### Этап 4. Только затем расширение

Chunking / модель embeddings → lexical fusion / reranking → релевантные графовые факты → ограниченный multi-hop retrieval.

**Проверка:** качество растёт на отложенных данных при приемлемой цене/latency. Если нет — не усложнять архитектуру ради названия.

## 9. Итоговая оценка

**Хороший учебный прототип с конкретными инженерными решениями, но не production-ready продукт и не доказанное улучшение над обычным RAG.**

На ревью сильнее всего выглядят: объяснение полного потока данных, понимание направлений и provenance, безопасная миграция, воспроизводимый mini-eval и готовность показать собственные ошибки. Главный следующий шаг — не «добавить ещё одну модель», а повысить корректность данных и качество измерения.
