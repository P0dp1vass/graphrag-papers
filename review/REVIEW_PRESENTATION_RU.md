# Как презентовать проект и отвечать на ревью

После обработки кода изменилось форматирование, затем скрипты были вручную отредактированы (убраны docstrings и комментарии). Номера строк ниже относятся к исходному аудиту; для текущих позиций используй [final_state.json](checks/final_state.json), [карту строк](checks/code_cleanup/line_map.json) или поиск по имени функции.

## 1. Короткая речь на 60–90 секунд

> Я сделал учебный GraphRAG по абстрактам научных статей arXiv. Offline pipeline получает статьи, локальная Qwen извлекает сущности и направленные отношения, Neo4j хранит граф и источники фактов. Отдельная embedding-модель кодирует статьи и вопросы.
>
> При запросе я нахожу три статьи через векторный поиск с дополнением точными названиями методов в заголовках. Затем добавляю до тридцати отношений именно из этих статей и передаю их вместе с полными абстрактами генератору. Интерфейс — FastAPI, ответы на английском.
>
> Я уделил внимание provenance, направлению рёбер, безопасной канонизации алиаса и тестируемому сравнению режимов. Сейчас это RAG с графовым обогащением, а не multi-hop поиск.
>
> На пяти development-вопросах граф не показал явного выигрыша, а генерация стала дольше. Поэтому я не заявляю улучшение качества: следующий шаг — строгая валидация данных, воспроизводимый запуск и больший отложенный eval. В разработке и разметке использовалась помощь ИИ; результаты и ограничения я проверяю и могу объяснить по коду.

Не заучивай звук в звук: перескажи своими словами, сохранив ограничения.

## 2. План выступления на 7–10 минут

### 0:00–1:00. Задача и рамки

«Отвечать по небольшому корпусу abstracts, а не по памяти LLM». Покажи схему offline/online из полного разбора. Сразу уточни: 500 входных статей, 498 Paper в БД, только английский QA, без UI.

### 1:00–2:30. Данные и граф

Открой `load_graph.py:16` и `qa.py:30`. Объясни Paper/Entity, MENTIONS, направленный R, type и source_ids. Приведи условный `A USES B`, объясни, почему нельзя перевернуть стрелку или заменить USES на IMPROVES.

Сильная фраза: «MENTIONS связывает документ с сущностью; source_ids связывает конкретное утверждение с документом. Это разные уровни provenance».

### 2:30–4:00. Retrieval и generation

Открой `retrieval.py:50` и `qa.py:63`. Покажи три статьи, exact title identifiers + ANN, затем relations и полные abstracts в prompt.

Расскажи реальный tradeoff: маленькая embedding-модель быстрая, но может пропустить редкое название. Title supplement исправляет конкретный failure mode, но скан всех titles плохо масштабируется.

Скажи прямо: entity vector search есть в коде, но в активном ask-пути не используется.

### 4:00–5:00. Надёжность и безопасное изменение графа

Открой `merge_actgcg.py:75`, затем `:230`. Dry-run → backup → сравнение snapshot → транзакция → post-check. Сохраняются canonical embedding, направления, union sources; конфликт вызывает отказ.

Не запускай `--apply` во время презентации. Уже выполненную миграцию можно показать по snapshot/report и тестам.

### 5:00–7:00. Проверка гипотезы

Открой сохранённый `.review.md` mini-eval. Объясни, что контексты одинаковы, различаются только graph facts; references не попадают в генератор.

Приведи 4/4 hit@3, 10/10 генераций без ошибок, 28.6/47.4 секунды и отсутствие явных побед графа. Тут же оговори маленькую development-выборку и AI-assisted оценку.

Покажи ошибку Bioformer: «40% от» ≠ «на 40% меньше». Это убедительнее, чем скрывать неудачный ответ.

### 7:00–8:30. Недостатки и roadmap

Выбери три, не перечисляй всё подряд:

1. Секреты/config/bootstrap.
2. Строгая schema + semantic validation, безопасный resume/ingestion.
3. Отложенный eval и релевантность фактов, затем возможный multi-hop.

Laya назови экспериментом со слабым precision на небольшой предварительной разметке, не «автоматическим верификатором».

### 8:30–10:00. Демо/вопросы

Покажи один английский вопрос и источник либо используй сохранённый результат с честной подписью «записанный прогон». Не импровизируй destructive maintenance.

## 3. Безопасное демо

### До встречи

- Проверить локальный Neo4j/Ollama, наличие model cache и состояние `paper_vec`.
- Знать, что API startup проверяет Neo4j и грузит embedding-модель, но не обеспечивает readiness Ollama/индексов.
- Прогнать unit-тесты; убедиться, что демонстрационные источники есть в corpus.
- Открыть сохранённый eval на случай долгой генерации. Средние 28–47 с — не обещание времени конкретного запроса.
- Не показывать на экране credentials из исходников и приватные настройки.

### Запуск только API, не ingestion

Из корня, при уже подготовленной БД:

```bash
.venv/bin/uvicorn app:app --app-dir scripts --host 127.0.0.1 --port 8000
```

В другом терминале:

```bash
curl --fail-with-body http://127.0.0.1:8000/health
curl --fail-with-body --max-time 200 \
  -H 'Content-Type: application/json' \
  -d '{"question":"What does RAG-FGO optimize, and how does its memory pool help?"}' \
  http://127.0.0.1:8000/ask
```

`--max-time` curl не меняет внутренний timeout приложения. Health 200 не означает, что Qwen или indexes готовы. Вывод live-запроса не обязан совпасть с сохранённым.

### Read-only Cypher для демонстрации

В Neo4j Browser, без вывода секретов:

```cypher
MATCH (p:Paper) RETURN count(p) AS papers;
```

```cypher
MATCH (a:Entity)-[r:R]->(b:Entity)
WHERE 'http://arxiv.org/abs/2611.17788v1' IN coalesce(r.source_ids, [])
RETURN a.name AS head, r.type AS relation, b.name AS tail, r.source_ids AS sources
ORDER BY head, relation, tail
LIMIT 10;
```

Это показывает записи extraction, не ручную сертификацию каждого факта.

**Во время демо не запускать:** `rebuild_relations.py`, `merge_actgcg.py --apply`, `load_graph.py`, `embeddings.py`, полный Laya filter или повторный extraction. Они меняют состояние и не нужны для показа API.

## 4. Вопросы ревьюера и честные ответы

### «Почему это GraphRAG?»

«В контекст попадают структурированные направленные связи с provenance из Neo4j. Но retrieval документов сначала векторный/title-aware; граф не расширяет документы. Поэтому точнее — RAG с графовым обогащением».

### «Чем это отличается от Microsoft GraphRAG?»

«Здесь нет community detection/summaries и local/global retrieval той архитектуры. Используется общая идея графовых знаний в RAG, не полное воспроизведение чужого framework».

### «Зачем граф, если abstract уже содержит информацию?»

«Гипотеза — явные связи помогут выделять отношения и объединять evidence. Сейчас они в основном повторяют найденные abstracts и иногда шумят. Эффект нужно доказывать отдельным eval; пока победы не показано».

### «Где multi-hop?»

«В текущем ask нет. Pattern Paper→Entity→Entity — не доказательство multi-hop reasoning: документы не расширяются, длинные цепочки не строятся».

### «Почему не просто SQL/обычный RAG?»

«Обычный RAG — обязательный baseline. Neo4j удобен для направленных связей и provenance/обходов, но для этого маленького корпуса может быть избыточен. Без измеренного выигрыша я не утверждаю, что он необходим».

### «Почему Qwen и MiniLM — две модели?»

«MiniLM кодирует смысл в 384-мерные векторы для retrieval; Qwen генерирует структуру и текст ответа. Embedding-модель не отвечает на вопросы, а генератор не заменяет поисковый индекс».

### «Почему k=3? Почему 30 фактов?»

«Это текущие фиксированные development-настройки, не оптимальные величины. Их нужно выбирать на dev-наборе по качеству/бюджету, затем оценивать на holdout. TOP_K=5 — оставшаяся константа, active paper retrieval использует 3».

### «Это гибридный retrieval?»

«В широком смысле есть dense ANN и точные title matches. Но это не BM25+dense fusion и не RRF: title matches приоритетнее, затем cosine и ID».

### «Почему не multilingual embeddings?»

«Целевая задача — английские abstracts и вопросы. Сначала нужно качественно оценить этот сценарий. Исторические русские вопросы не доказывают multilingual-качество текущей модели».

### «Почему 500 статей на входе и 498 в графе?»

«Extraction содержит 498 уникальных IDs. Две статьи не представлены; текущие артефакты не позволяют надёжно назвать причину каждой. Дополнительно есть повторные JSONL-записи — это проблема resume/данных, а не ещё 24 новые статьи».

### «MERGE гарантирует корректный граф?»

«Нет. Он помогает не создавать тот же pattern повторно; constraints защищают ключи. Неверная тройка останется неверной. Кроме того, текущая загрузка не атомарна на статью».

### «Источник на ребре означает доказанный факт?»

«Нет, это provenance автоматической extraction. Нужно сверить смысл, направление и evidence span в abstract. Поэтому prompt считает abstract первичным evidence и предупреждает о ненадёжных relations».

### «Почему не слить все похожие имена?»

«Похожесть строки не доказывает тождество сущности. Я начал с одного согласованного алиаса и безопасной миграции. Для общего решения нужны candidates, типы/контекст, review и версия mapping».

### «Насколько хорошо работает Laya?»

«На 18 предварительно размеченных случаях TP=3, FP=8, FN=0, TN=7, precision 27.3%. Разметка AI-assisted, token truncation исходный eval не сохранял, есть несовпадения версий/онтологических правил. Поэтому это исследовательская ветка, не обязательный фильтр».

### «Confidence — это вероятность истины?»

«Нет. Концентрация распределения и даже калиброванный answer confidence не заменяют проверку поддержки claim в источнике. Калибровку нужно измерять на своём распределении задач».

### «Как вы оценивали пользу графа?»

«На пяти вопросах заморозили одинаковые top-3 статьи и abstracts; режимы различались только graph facts. Сохранили prompts, usage, timing и errors. Это чистая ablation контекста, но маленькая development-проверка, не независимый benchmark».

### «У вас hit@3=100%. Значит, всё правильно?»

«Нет, это 4 попадания из 4 answerable-кейсов. Retrieval нашёл нужный источник, но generator всё равно ошибся с процентом параметров. Нужны отдельные метрики поиска, фактов ответа и цитирования».

### «Почему ссылка почти всегда отсутствует?»

«Prompt требует URL, но маленькая локальная модель часто не следует инструкции. Сейчас только 1/4 содержательных ответов содержит URL в каждом режиме. Нужны structured citations и проверка claim→evidence, а не только ещё одно предложение в prompt».

### «Какой результат вы считаете неудачей?»

«Bioformer: источник говорит 40% от параметров, оба ответа говорят на 40% меньше. Время генерации с графом тоже выше без ясного выигрыша. Эти ошибки зафиксированы, не исключены из отчёта».

### «Что покрывают 36 тестов?»

«Pure/mocked retrieval, planning миграции и инварианты eval. Они не заменяют интеграционные тесты Neo4j/Ollama и независимую оценку качества текста».

### «Почему не всё async?»

«Async полезен с неблокирующими I/O библиотеками. Здесь requests и encode синхронные; async def сам по себе их не ускорит. Сначала concurrency limit, очередь и нагрузочные измерения, затем обоснованная смена I/O слоя».

### «Production-ready?»

«Нет. До внешнего доступа нужны secrets/config/auth/limits; затем строгая валидация, cleanup ресурсов, reproducible bootstrap, integration tests, monitoring и качественный eval».

### «Вы сами написали и понимаете код?»

«В разработке использовалась помощь ИИ. Я отвечаю за проверку и могу пройти путь от запроса до источника, объяснить транзакции, ranking и ограничения. Если чего-то не знаю, покажу соответствующий участок и проверю, а не буду угадывать».

### «Что сделал watermark-remover?»

«Локально установлен. Сначала выполнили read-only аудит, затем по отдельному запросу — обработку всех Python-файлов: форматирование и редактуру комментариев; после этого я вручную убрал docstrings и комментарии из скриптов. До и после обработки Unicode-находок нет; AST и строки совпадали, 36 тестов проходят. Это не code reviewer и не доказательство авторства; помощь ИИ не скрывается».

## 6. План подготовки

### Проход 1 — понять поток

Нарисуй архитектуру по памяти. Устно объясни каждую стрелку: вход, выход, format, место ошибки. Открой `qa.ask` и дойди до HTTP-запроса в Ollama.

### Проход 2 — проверить понимание кода

Пройди `CODE_WALKTHROUGH_RU.md`, не просто читай: предскажи результат rank_candidates, неизвестного relation и повторного ingestion. После этого сверься с кодом и `checks/`.

### Проход 3 — выучить главное

Анки: сначала `priority::core`, затем темы своих пробелов. Не пытайся учить все карточки одним вечером; начинай с 15–25 новых в день, делай регулярные повторения.

### Проход 4 — репетиция

Запиши 8-минутное выступление без текста. Проверь: не назвал ли dev-eval benchmark, не приписал ли графу пользу, можешь ли объяснить 40%/60%, source_ids, k=3 и API cleanup.

### Проход 5 — контроль перед ревью

- [ ] За минуту объясняю назначение и ограничения.
- [ ] Показываю active ask path, не неиспользуемые helper-функции.
- [ ] Различаю JSON syntax, schema и semantic correctness.
- [ ] Объясняю MERGE, constraints, transaction и provenance.
- [ ] Объясняю title ranking и ограничения MiniLM.
- [ ] Точно описываю ablation и ограничения оценивания.
- [ ] Знаю три приоритетных улучшения и критерии их проверки.
- [ ] Не показываю секреты и не запускаю destructive scripts.
- [ ] Не выдаю помощь ИИ за независимое экспертное заключение.

Если не знаешь ответ: «Сейчас не могу подтвердить. Предположение такое-то; я проверю его таким-то тестом». Это лучше неподтверждённой уверенности.
